1. Project Overview & Motivation

What is QuickShow?

QuickShow is a modern, production-grade movie ticket booking web application that simulates a real-world cinema platform end-to-end. It features real-time movie listings fetched from the TMDB API, an interactive seat selection grid with temporary seat-locking to prevent double-booking, Stripe-powered payments, custom JWT + bcrypt authentication with dedicated login/register pages, and a transport/cab booking module with live mapping via OpenStreetMap and Leaflet.

Core Problems Solved

  • Concurrency / Double-Booking: Multiple users selecting the same seat simultaneously is a classic distributed-systems problem. QuickShow uses a 10-minute pending-booking lock pattern to guarantee no two users can pay for the same seat.
  • Real-Time Data: Movie listings are always current because they are proxied from the TMDB API with retry logic, not from a stale database.
  • Seamless Auth: Custom JWT + bcrypt authentication with a React AuthContext provides seamless signup/login via dedicated pages. Passwords are securely hashed with bcrypt and sessions are managed via JSON Web Tokens stored in localStorage.
  • Last-Mile Transport: After booking tickets, users can book a cab to the theatre directly within the platform using geolocation and nearest-theatre discovery.

Booking Model (Booking.js) — ★ Critical for Seat Locking

const bookingSchema = new mongoose.Schema({
  user:            { type: String, required: true },   // MongoDB User ObjectId (stored as string)
  movie:           { type: Number, required: true },   // TMDB movie ID
  movieTitle:      { type: String, required: true },
  moviePoster:     { type: String },
  showDateTime:    { type: Date, required: true },
  bookedSeats:     { type: Array, required: true },    // ["A1", "A2", "B3"]
  amount:          { type: Number, required: true },   // Total price
  isPaid:          { type: Boolean, default: false },   // ★ Lock flag
  stripeSessionId: { type: String },
}, { timestamps: true })   // ★ createdAt used for 10-min lock expiry
⚠️ The Dual-Purpose Booking Record: A booking record with isPaid: false acts as a temporary seat lock. The createdAt timestamp (auto-generated by timestamps: true) determines when the lock expires (10 minutes). After payment, isPaid is flipped to true, making it a permanent booking.

Dual Entry Points

The server has two entry points to support both local development and Vercel serverless deployment:

  • Calls connectDB() once at startup (eager connection)

  • Connection is cached via isConnected flag in db.js
  • Exported as export default app — Vercel wraps it as a serverless function
  • The vercel.json rewrite "/(.*)" → "/api/index" routes all requests to this file

Database Connection (db.js)

let isConnected = false;

const connectDB = async () => {
    if (isConnected) return;          // Skip if already connected
    try {
        await mongoose.connect(process.env.MONGODB_URI, {
            serverSelectionTimeoutMS: 10000,  // 10s to find a server
            socketTimeoutMS: 45000,           // 45s socket timeout
            bufferCommands: false,            // Fail fast if disconnected
        });
        isConnected = true;
        console.log('DB Connected');
    } catch (error) {
        console.log('DB Connection Error:', error.message);
    }
}

The singleton pattern (isConnected flag) ensures only one connection is established, critical for serverless where multiple invocations share the same module scope within a warm container.

8. Seat Locking & Double-Booking Prevention (In-Depth)

🎯 THE MOST IMPORTANT FEATURE TO UNDERSTAND
This is the #1 interview topic for this project. The seat locking mechanism prevents the "race condition" where two users simultaneously select and pay for the same seat.

The Problem

User A selects seat A1 at 10:00:00. User B selects seat A1 at 10:00:05. Both proceed to Stripe checkout. Without locking, both could pay successfully, resulting in a double-booking. Who gets the seat? Who gets a refund?

The Solution: Pending-Booking Lock Pattern

QuickShow uses the Booking model itself as both a lock and a final booking record. There is no separate "lock" collection. The isPaid boolean and createdAt timestamp together determine whether a booking is a temporary lock or a finalised ticket.

How It Works — Step by Step

Step 1: Fetching Seat Status (GET /seats-status)

router.get('/seats-status', async (req, res) => {
    const { movieId, showTime } = req.query;
    
    const bookings = await Booking.find({
        movie: Number(movieId),
        showDateTime: new Date(showTime)
    });

    const occupiedSeats = [];   // Permanently booked (paid)
    const lockedSeats = [];     // Temporarily locked (unpaid, < 10 min)
    const tenMinutesAgo = new Date(Date.now() - 10 * 60 * 1000);

    bookings.forEach(booking => {
        if (booking.isPaid) {
            occupiedSeats.push(...booking.bookedSeats);    // ★ Paid = permanent
        } else if (booking.createdAt > tenMinutesAgo) {
            lockedSeats.push(...booking.bookedSeats);      // ★ Unpaid + recent = locked
        }
        // Else: unpaid + older than 10 min = expired lock (ignored)
    });

    res.json({ success: true, occupiedSeats, lockedSeats });
});
💡 Three Seat States:
  • Available — No booking record, or only expired unpaid records
  • Locked (amber) — Unpaid booking created within the last 10 minutes
  • Occupied (red) — Paid booking exists

Step 2: Creating a Checkout Session (POST /create-checkout-session)

router.post('/create-checkout-session', async (req, res) => {
    const { seats, movieId, movieTitle, moviePoster, showTime, amount, userId } = req.body;

    // ★ STEP A: Re-verify availability at checkout time
    const existingBookings = await Booking.find({
        movie: Number(movieId),
        showDateTime: new Date(showTime)
    });

    const occupiedSeats = new Set();
    const lockedSeats = new Set();
    const tenMinutesAgo = new Date(Date.now() - 10 * 60 * 1000);

    existingBookings.forEach(booking => {
        if (booking.isPaid) {
            booking.bookedSeats.forEach(seat => occupiedSeats.add(seat));
        } else if (booking.createdAt > tenMinutesAgo) {
            booking.bookedSeats.forEach(seat => lockedSeats.add(seat));
        }
    });

    // ★ STEP B: Reject if ANY seat is taken/locked
    const isAnySeatUnavailable = seats.some(
        seat => occupiedSeats.has(seat) || lockedSeats.has(seat)
    );
    if (isAnySeatUnavailable) {
        return res.status(400).json({
            success: false,
            message: 'One or more seats are already locked or booked.'
        });
    }

    // ★ STEP C: Create unpaid booking = LOCK the seats
    const booking = await Booking.create({
        user: userId || 'guest',
        movie: movieId,
        movieTitle, moviePoster,
        showDateTime: showTime,
        bookedSeats: seats,
        amount,
        isPaid: false,           // ← This IS the lock
    });

    // ★ STEP D: Create Stripe Checkout Session
    const session = await stripe.checkout.sessions.create({
        payment_method_types: ['card'],
        line_items: [{ ... }],
        mode: 'payment',
        success_url: `${CLIENT_URL}/my-bookings?success=true&bookingId=${booking._id}`,
        cancel_url: `${CLIENT_URL}/movies`,
        metadata: { bookingId: booking._id.toString() }
    });

    res.json({ success: true, url: session.url });
});

Lock Expiry

If User A doesn't complete payment within 10 minutes, the lock expires passively:

  • The unpaid booking's createdAt becomes older than Date.now() - 10 * 60 * 1000
  • The seats-status endpoint and the checkout verification automatically ignore it
  • No cron job or TTL index needed — expiry is computed at read-time

18. Interview Questions & Answers (80+)

🎯 Project Overview Questions

Q1. What is QuickShow? Give a brief overview.

QuickShow is a full-stack movie ticket booking web application built with React 19, Vite, Tailwind CSS v4 on the frontend and Express.js, MongoDB, Stripe, and Clerk on the backend. It features real-time movie listings from the TMDB API, an interactive seat selection grid with a 10-minute temporary seat-locking mechanism to prevent double-booking, Stripe payment integration, Clerk-based authentication with Inngest background webhooks for user sync, and a Transport module for booking cab rides to theatres using Leaflet maps and OpenStreetMap APIs.

Q2. What problem does QuickShow solve?

It primarily solves the concurrency/double-booking problem in ticket booking systems. When multiple users try to book the same seat simultaneously, QuickShow's pending-booking lock pattern ensures only one user can proceed with payment. It also solves the problem of stale movie data by proxying real-time TMDB API data, and integrates last-mile transport booking within the same platform.

Q3. What are the three architectural tiers in this project?

1) Fully Integrated Live Flows — Authentication (JWT+bcrypt→MongoDB), movie listing (TMDB API), seat locks and checkout (Booking model), payment verification (Stripe). 2) Client-Side External Integrations — Theatre discovery (OSM Nominatim), routing (OSRM), Haversine distance filter, OTP simulation. 3) Static Admin Mockups — Dashboard, AddShows, ListShows, ListBookings use local dummy data and are not connected to the backend.

Q4. Why did you choose React + Vite over Next.js?

QuickShow is a client-rendered SPA that doesn't need server-side rendering or static generation. Vite provides extremely fast HMR (Hot Module Replacement) during development and efficient bundling. The backend is a separate Express.js server, maintaining a clean separation of concerns. This architecture also simplifies deployment — the client deploys as a static SPA on Vercel, and the server deploys as a separate serverless function.

🔐 Seat Locking & Concurrency Questions

Q5. Explain the seat-locking mechanism in detail.

When a user clicks "Proceed to Checkout", the backend creates a Booking document with isPaid: false. This unpaid booking serves as a temporary lock. The createdAt timestamp (auto-generated by Mongoose's timestamps: true) marks when the lock was created. When other users fetch seat status, the backend checks all bookings for that show: paid bookings → occupied (permanent), unpaid bookings created within the last 10 minutes → locked (temporary), unpaid bookings older than 10 minutes → expired (ignored). If someone tries to checkout seats that are locked/occupied, the backend returns a 400 error.

Q6. How do you determine if a seat is locked, occupied, or available?

Three states: Occupied = booking exists with isPaid: true. Locked = booking exists with isPaid: false AND createdAt > (now - 10 minutes). Available = no booking matches, or only expired unpaid bookings exist. This is computed at query time using const tenMinutesAgo = new Date(Date.now() - 10 * 60 * 1000).

Q7. Why 10 minutes for the lock duration?

10 minutes is a reasonable balance — long enough for users to complete the Stripe checkout process (entering card details, OTP verification), but short enough that abandoned locks don't block seats for too long. In production, this could be configurable via an environment variable.

Q8. How does the lock expire? Is there a cron job?

No cron job or TTL index is needed. The expiry is computed at read time. When any user fetches seat status or attempts checkout, the backend calculates tenMinutesAgo and simply ignores unpaid bookings older than that. This is a passive/lazy expiry pattern — elegant and requires zero infrastructure.

Q9. Is there a race condition between two users checking out the same seat at the exact same millisecond?

In theory, yes — since the check-and-create are not atomic (they're separate MongoDB operations). In practice, this is extremely rare for a cinema booking app. To make it fully atomic, we could use MongoDB transactions (session.startTransaction()) or use a unique compound index on {movie, showDateTime, bookedSeats} to prevent duplicate inserts. For this project's scale, the current approach is pragmatic and effective.

Q10. What happens on the frontend when a seat lock conflict is detected?

The checkout endpoint returns {success: false, message: "seats already locked or booked"}. The frontend shows a toast notification with the error message, clears the user's seat selection, and re-fetches seat status (fetchSeatStatus()) so the UI immediately reflects the latest state. The user can then select different available seats.

Q11. Why use unpaid Booking records instead of a separate Lock collection?

Using the same collection avoids data duplication and simplifies the data model. The booking record serves dual purposes — it's a lock when isPaid: false and a permanent record when isPaid: true. There's no need to "move" data from a Lock collection to a Booking collection on payment. It's a single findByIdAndUpdate(id, {isPaid: true}) to finalize.

Q12. What is the maximum number of seats a user can select at once?

5 seats. This is enforced on the frontend in SeatLayout.jsx: if (!selectedSeats.includes(seatId) && selectedSeats.length >= 5) return toast("You can only select 5 seats"). This prevents abuse and is a common real-world constraint.

💳 Stripe Payment Questions

Q13. How does the Stripe payment flow work?

1) Client sends seat selection to /create-checkout-session. 2) Backend verifies seat availability, creates an unpaid booking (lock), then calls stripe.checkout.sessions.create() with product details, amount (in paisa), success/cancel URLs. 3) Backend returns the Stripe session URL. 4) Client redirects to Stripe's hosted checkout page via window.location.href. 5) On success, Stripe redirects to /my-bookings?success=true&bookingId=X. 6) MyBookings component calls /verify/:bookingId which sets isPaid: true.

Q14. Why use Stripe Checkout (hosted) instead of Stripe Elements (embedded)?

Stripe Checkout is a pre-built, hosted payment page that handles card input, validation, 3D Secure, PCI compliance, and mobile responsiveness out of the box. It reduces development effort and security liability. Stripe Elements would require building the form UI ourselves and handling more edge cases.

Q15. Why is unit_amount multiplied by 100?

Stripe requires amounts in the smallest currency unit. For INR, that's paisa (1 rupee = 100 paisa). So ₹150 is sent as 15000. This avoids floating-point precision issues.

Q16. What happens if the user clicks "Cancel" on Stripe?

Stripe redirects to the cancel_url (/movies). The unpaid booking remains in the database but will automatically expire after 10 minutes (passive expiry). No cleanup is needed.

Q17. Is the payment verification secure? Can someone call /verify directly?

Currently, the /verify/:bookingId endpoint is called by the client after Stripe redirects. In a production system, you should use Stripe webhooks instead — Stripe sends a checkout.session.completed event to your server, which is cryptographically signed. The current approach is simpler but less secure for production.

🔑 Authentication Questions

Q18. How does authentication work in this project?

On the client, AuthProvider (React Context) manages global state, storing a JWT token in localStorage and providing a useAuth() hook to access user data. On the server, custom routes (/api/auth/register, /api/auth/login) handle credential validation. Protected routes use an authMiddleware that verifies the JWT from the Authorization: Bearer <token> header.

Q19. How are passwords stored securely?

Using bcrypt (via the bcryptjs library). When a user registers, the plaintext password is salted (using bcrypt.genSalt) and hashed (using bcrypt.hash) before being saved to MongoDB. When logging in, bcrypt.compare is used to verify the submitted password against the stored hash. Plaintext passwords are never stored or logged.

Q20. Why use JWT for session management instead of cookies?

JWTs (JSON Web Tokens) are stateless, meaning the server doesn't need to store session data in memory or a database—the token itself contains the authenticated user's ID payload. Storing it in localStorage makes it easy to attach to API requests as a Bearer token, which is highly compatible with decoupled frontend/backend architectures and mobile apps.

Q21. Why did you switch from a hosted provider (like Clerk) to custom JWT+bcrypt?

While hosted providers offer quick setup and robust features, a custom implementation provides complete control over user data and the authentication flow. It avoids vendor lock-in, eliminates the need for webhook-based synchronization (which can introduce latency or point of failure), and serves as a stronger demonstration of fundamental backend security concepts.

🎬 TMDB API Questions

Q22. Why proxy TMDB API calls through your backend?

Three reasons: 1) Security — the TMDB API key stays on the server and is never exposed to the browser. 2) Transformation — the server maps raw TMDB data to a clean schema with full-resolution image URLs and genre name lookups. 3) Resilience — the fetchWithRetry function automatically retries failed requests up to 3 times.

Q23. How does the retry logic work?

fetchWithRetry loops up to 3 times. Each iteration calls axios.get() with a 10-second timeout. If it throws an error and it's not the last attempt, it logs a retry message and loops again. On the final failure, the error propagates to the route handler which returns a 500 response.

Q24. How does the language filter work?

The /now-playing endpoint accepts an optional ?language= query parameter. After fetching all now-playing movies from TMDB, the server filters by original_language if the value isn't 'all'. Supported: en (English), hi (Hindi), te (Telugu), ta (Tamil). This is done server-side for efficiency.

Q25. What is the genreMap and why is it needed?

TMDB's now-playing endpoint returns genre_ids (numeric arrays like [28, 12]) but not genre names. The genreMap object maps each ID to its human-readable name (e.g., 28 → "Action"). This avoids an extra API call to TMDB's /genre/movie/list endpoint.

🗺️ Transport & Maps Questions

Q26. How does the theatre discovery feature work?

The client uses the browser's Geolocation API to get the user's coordinates. It then queries OSM Nominatim for "cinema" POIs within a bounding box (±0.18 degrees from user location, roughly 20km). Results are further filtered using the Haversine formula to ensure they're strictly within a 20km radius.

Q27. What is the Haversine formula and why is it used?

The Haversine formula calculates the great-circle distance between two points on a sphere given their latitudes and longitudes. It's used because the Nominatim bounding box search returns results within a square region, but we need a circular 20km radius. The Haversine filter ensures only theatres truly within 20km are kept.

Q28. How is the driving route rendered on the map?

Q31. How is the database connection cached in serverless?

The db.js module uses a module-level isConnected boolean flag. On the first request (cold start), connectDB() establishes the connection and sets isConnected = true. Subsequent requests in the same warm container skip the connection. This is essential for serverless performance.

Q32. Why use Express v5 instead of v4?

Q56. How would you wire the admin dashboard to the live API?

🔥 Advanced & Tricky Questions

Q71. If two users select the same seat and click checkout within the same millisecond, what happens?

Both POST requests hit the backend nearly simultaneously. The first request to complete the Booking.create() call wins — it creates the unpaid booking. When the second request runs the availability check, it sees the seat is now locked by the first booking and returns a 400 error. However, there's a tiny window between the check and create where both could pass — this is the classic TOCTOU (Time of Check / Time of Use) vulnerability. For absolute safety, use MongoDB transactions or a unique compound index.

Q72. How would you implement a waiting queue for sold-out shows?

Create a WaitlistEntry model with {user, movie, showDateTime, createdAt}. When all seats are occupied, show a "Join Waitlist" button. If a lock expires or a booking is cancelled, check the waitlist and notify the first user via email/push notification with a time-limited reservation.

Q73. How would you add a refund feature?

Use stripe.refunds.create({ payment_intent: booking.stripePaymentIntentId }). This requires storing the paymentIntentId from the Stripe session (via webhook or session retrieval). Then set isPaid: false and isRefunded: true on the booking to free up the seats.
